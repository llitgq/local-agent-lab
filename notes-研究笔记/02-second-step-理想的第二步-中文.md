# 📝 02 · 理想的第二步：先吃透配置，再谈让它干活

[English](02-second-step-理想的第二步.md)

> 装好智能体，尝鲜谁都会——聊一聊、看看它能做这个做那个，这个阶段人人都要过。但尝鲜完，接下来该研究什么？我的答案可能和直觉相反：**不是先研究让它做什么，而是先吃透配置。**
>
> 2026-10-30

## ⚙️ 先研究配置，而不是"它能替我干什么"

- 把**所有配置选项**搞清楚：每一项是干什么的、动它会改变什么
- **API 怎么接**、**免费模型怎么换**——如果你用免费模型，"换模型、换 API"就是最高频的操作，没有之一
- 这一步可以让电脑上装的免费智能体替你操作，但要有心理准备：**会耗掉大量时间和 token**。初期把配置啃明白了，后面能省掉数不清的弯路

反面教材还是我：我曾经专门写过**三四个 Skill**，就为了绕开"读懂配置、改 AI 模型"这件事。绕来绕去才发现，根子是配置没吃透。

## 👤 user / memory / Skill：一个一个来

配置之后，是把自己的 **user（用户画像）和 memory（记忆）写好**。

然后是 Skill。我的原则：**每上一个 Skill，就要清楚一个 Skill 的用途——它到底是干什么的、什么时候用。** 千万不要下载一堆 Skill 回来，既不知道要配什么，也不清楚它的运行逻辑，最后变成 Skill 的堆积——堆积的 Skill 不是资产，是负债。

## 🔗 工具联动：别让输出端掉队

我在社群里和身边朋友身上看了太多：飞书端收到的界面、文字，和智能体配置端**根本没有形成联动**；微信里的表格至今还是 Markdown 裸格式。飞书配置好以后体验会好很多，但飞书自己的设置并不完善——默认不会走飞书卡片，就很麻烦。

这里我写了一个小工具（后续会发上来）：智能体 + 飞书搭配，加一层拦截——**所有带表格的输出统一用飞书卡片发送**。前提是你用飞书做联络端。

## 🧩 别急着上多智能体

很多事一个智能体就能做。个人建议：**设大类，不设小类。** 不是"饮食助手 + 运动助手 + 睡眠助手"，而是一个"生活助手"，把健身、饮食这些都装进去。分得太细，管理和切换成本会把收益吃掉。

## 💻 摸一摸自己机器的底

我对电子设备其实不算了解。一开始觉得 Mac mini 内存太小、什么本地模型都跑不了——后来发现**本地识图、OCR、音频转文字都能跑**，前提是选对参数量级。别高估机器，更别低估机器。

## ⏰ 定时任务：从"死循环"到 job

定时任务我折腾过很长一阵子，想让**定时任务自循环**：一个写死的定时任务只在固定时间执行，而且你不知道那一刻 AI 的 token 还剩不剩、额度用没用完。尝试很多次，**皆以失败告终**。

后来才发现正路是多研究 **job（任务清单）**：把一个任务拆成多个细节步骤，而且**每个小步骤都带回测**。这很重要——代价是相对费一些 token，但可靠性完全不是一个量级。

## 🧪 多应用尝试，别在一棵树上吊死

不要只守着一个本地智能体。**OpenClaw、Claude Code Desktop、Claude Code 命令行**，都装来用一用。

我最初对 Claude Code 有两个偏见：一是觉得容易封，二是觉得接入麻烦。后来发现都不是——现在下载 Claude Code Desktop 或者装 CLI，再装一个 **CC Switch**，就能把 Claude Code 路由到自己的 API，没有任何特别难的步骤。

说句反省的话：我在 OpenClaw 和 Hermes 里浪费了太长太长的时间。Claude Code 的对话能力可能不是最强，但**接上 API 模型之后，它做事的能力会有质的提升**——你真的坐在工位上，它是真的能替你干活的那一个，产出相当可观。

## 🎯 一句话总结

第二步 = 吃透配置 + 写好 user/memory + 少而精的 Skill + 设大类 + 摸清机器底线 + 定时任务 job 化 + 多应用横向试。**先把自己武装明白，再让智能体替你上场。**
